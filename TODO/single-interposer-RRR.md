更新日期：2026-10-23。状态：已实现，主要验收完成；旧回归失败及 GUI 环境限制见执行记录 `.plan/2026-10-23-single-interposer-RRR.md`。

## 1. 目标与范围

保留当前初始排序、资源分配及一轮顺序 maze route，在首轮结束或首次失败后，接入指定 FPIA-RRR 的 AIR 场景适配算法，提升布通能力并优化合法解的总线长。增加可选布线时间预算，正确保存和恢复最优完整合法解，最终生成与该解一致的 controlbits。

本次以 `source/algo/router` 的非增量、单 interposer Maze 流程为主要修改对象；按需修改参数传递、CLI 状态处理及测试。保留现有 SAT/ILP、输入、布局、输出和 GUI 调用的兼容性，不扩展多 interposer 或恢复增量 CLI 功能。

“一模一样移植”指移植指定代码的搜索、资源、代价、拆线和同步线策略；初始化接入、终止条件、结果提交和日志按本次需求适配。参考目录的旧工程范围约束和旧停止行为不作为本项目的新需求。

## 3. 已确认的行为

### 3.1 初始布线与交接

1. 沿用现有排序和资源处理，执行现有顺序 maze route；不在首轮提前替换成 RRR 搜索策略。
2. 首轮全部成功：验证整体合法性，保存第一份最优解，并将本次合法解计入收敛计数。
3. 首个 net 失败：停止初始顺序布线，清理该 net 的部分路径及其资源占用，保留此前成功 net 的有效路径，然后转入 RRR。
4. 尚未处理的 net 作为未布通需求进入 RRR；不能漏掉失败 net 或后续 net。
5. SyncNet 失败时按整个同步组清理，避免部分 lane 残留。
6. 初始失败是阶段状态；RRR 修复成功后最终状态必须成功，不能被首轮遗留失败列表阻止输出。

当前 `command_mode/command/route.cc` 捕获失败后还会继续后续 net，本次需在目标 Maze 流程中改为首次失败交接；避免改变 SAT 或其他无关调用路径。

### 3.2 合法解与优化目标

完整合法解须满足所有待布 net 的端口连通、路径/树结构有效、资源容量与物理开关约束成立，以及同步组等长。尤其检查 TOB 第三级 straight/swap 互斥、mux 选择兼容、unit 约束及同步 lane 之间的资源冲突。

最优解仅在完整合法的候选中按总线长比较。采用项目和参考实现的 Track+Bump 物理并集口径，避免多端树共享前缀重复计算；Sync 等长比较仍遵循现有 lane 长度语义。相同线长保留较早解，不以拥塞 cost 替代实际线长目标。

保存的最优解必须与正在修改的候选状态相互独立。终止时恢复该解的全部路径、连接器选择及必要硬件状态，再执行最终校验与输出。部分解、含冲突解和旧寄存器残留都不得作为成功结果输出。

### 3.3 不限时：三次合法解收敛

**首次找到合法解计为 1；此后出现严格更短的合法解时，该新解也作为新一段计数的第 1 次。** 在此基础上再出现两次未缩短最佳总线长的完整合法解，即达到 3 次并停止。

建议状态为 `best`、`best_length`、`legal_streak`：

```text
首次完整合法：保存 best，legal_streak = 1
后续完整合法且 length < best_length：更新 best，legal_streak = 1
后续完整合法且 length >= best_length：legal_streak += 1
不完整或不合法：不更新 best，不增加或清零 legal_streak
没有时间预算且 legal_streak >= 3：停止并恢复 best
```

这里的“连续”按完整合法解出现的序列计数；RRR 中间的非法修复轮不计数。未发生重布而重复检查同一个状态，不得重复算成新的一次合法解。

| 依次出现的完整合法解线长 | 计数变化 | 结果 |
| --- | --- | --- |
| 100、100、100 | 1、2、3 | 第三次停止，返回 100 |
| 100、90、90、90 | 1、1、2、3 | 第四次停止，返回 90 |
| 100、105、102 | 1、2、3 | 第三次停止，恢复 100 |
| 首轮 100、非法修复、100、100 | 1、不变、2、3 | 返回 100 |

不限时且一直没有完整合法解时，不满足收敛条件；不添加未经要求的迭代数上限或停滞退出条件。系统测试必须有外部超时防护，防止不可布通用例挂住测试进程。

### 3.4 限时：预算到即停止求解

- 预算覆盖整个布线阶段：初始排序/资源处理、首轮 maze、RRR 建图和参考长度计算、RRR 搜索与优化；不包含输入解析、布局及最终文件写出。
- 设置预算时按预算运行，不因上述三次合法解条件提前收敛；未设置预算时使用三次合法解收敛。
- 使用单调时钟和统一 deadline，不能在进入 RRR 时重新开始预算。
- 到时无论是否已经有完整合法解，都停止搜索；不继承参考实现“超时无解仍继续到首次合法”的行为。
- 已有最优合法解：清理当前候选并恢复最优解，校验后允许输出；当前解非法或更差不影响已保存结果。
- 尚无完整合法解：明确返回未找到合法解，跳过成功 controlbits 写出；不能把“在预算内未找到”表述为“已证明不可布通”。
- 截止检查须进入耗时搜索内部，包括首轮 maze、参考搜索、普通 RRR 搜索、同步等长搜索和必要长循环，不能仅在 net 或轮次边界检查。
- 超时取消后的清理、恢复、校验与写出可能使进程总墙钟时间略超过预算；它们不再继续求解。测试应验证搜索取消的延迟上界，而非要求进程精确在某毫秒退出。

**CLI（用户最终确认）：**采用 `--time-limit <seconds>`，单位统一为秒，允许正的有限小数；省略表示不限时。Maze 中限制整个布线阶段；SAT/ILP 保留原来的 ILP 阶段范围，仅将单位改为秒，仍须与 `--ilp-optimize` 同用。旧脚本中的小时数需要乘以 3600；已有 flow 测试的 5 小时参数已改为 18000 秒。本次不新增 `--route-time-limit`。拒绝缺值、负数、零、NaN/Inf 和非数值。用户后续明确不要求运行 SAT/ILP 验证。

## 4. RRR 核心移植内容

### 4.1 算法策略

- 独立计算每个 net 的无拥塞参考长度；参考搜索不能占用正式资源或污染历史代价，失败标记为 unavailable，不用 0 代替。
- 正式 RRR 状态由首轮已有路径初始化，区别于参考程序从空解开始。导入时同时重建 owner、tree、已连接 sink、占用和空间索引。
- 按参考实现的既定顺序补布未连通 sink，保留有效根树；新分支必须恢复完整 root→sink 关系。
- 总端口数至少 16 时启用附近 bin 树节点搜索，附近为空或失败时回退整棵树；阈值、bin 计算和回退语义保持参考实现一致。
- 动态 bbox 按参考实现移植：单次搜索固定框，轮末按成功路径触边情况扩框，保留外侧 Track/I/O 的物理边界。笔记中的搜索中扩框表述与此不同，不另行混用或添加全图兜底。
- 允许 RRR 候选暂时跨 net 拥塞；维护实时占用，并在同一轮末冲突快照上决定拆线。
- 大树从首个冲突位置剪除下游，清理失去 root 连通性的片段，保留合法根前缀及未受影响 sink；小 net 和同步组按参考规则整体拆除。
- 仅当前完整合法时执行主动线长拆线；当前非法时只做冲突修复，即使此前曾有合法解也一样。
- 线长拆线优先选择超过参考长度的 net；无候选时按参考实现退回多端 net，再退回全部 net。
- 同步线维持现有业务等长语义，移植参考实现中的预布、切尾、目标更新、整组回滚和互斥规则，不改成普通独立 net。

参考实现可能因失败 net 的 bbox 不扩张而持续失败；本次不自行改变这一策略。通过真实用例记录影响，限时模式按要求返回当前结果。

### 4.2 OpenROAD 代价

沿用参考实现已适配到图节点的形式：

```text
q(v) = usage(v) + 0.9 * history(v)        # red = 0, C = 1
c(v) = 1 + H / (1 + exp(k * (1 - q(v))))
         + (H / s) * max(q(v) - 1, 0)
H = 4, k = 1, s = 20
history_next(v) = history(v) + max(0, usage(v) - 1)
```

以上默认值、使用当前占用而非候选 `+1`、同 owner 已有树节点不重复收费、仅图节点计费等细节需逐项与源码核对并测试。开关/mux/mode 等非计费约束仍须参加冲突检测和合法性校验。历史不衰减、不在找到合法解后清空，不混入 VPR `pres_fac` 重置机制。

### 4.3 工程适配与状态边界

- 结合 `route_nets`、`RouteEngine`、Maze 后端和 `PathPackage` 的现有接口确定最小接入点，避免引入第二套对外布线流程。
- 参考实现使用独立 `ResourceModel`，不直接维护生产 `suspend/give_out/connect_all` 状态，也不输出 controlbits；不能仅复制主循环就认定移植完成。
- 明确“首轮生产路径 → RRR 图路径/资源 → 最优图路径 → 生产 PathPackage/硬件”的双向映射，核对 TOB 连接器、COB 开关、同步组与特殊 net。
- 首轮成功解必须先保存，避免耗时参考初始化或后续取消导致已知可行解丢失。
- 确保逻辑 net、owner、demand、Sync lane 的身份稳定；布局后使用实际端口坐标，不沿用布局前坐标。
- 失败、取消和恢复都需释放准确的资源，不能误清其他已保留 net，也不能双重占用或只恢复路径列表。
- 最优解恢复后重新构造并检查占用；最终 Writer 只消费该解对应的 PathPackage。
- 错误/终止原因与是否有可输出解分别表达：收敛成功、超时有解、超时无解及真正执行错误不能混淆。避免无依据扩展公共 API。

### 6.3 系统端到端测试

```text

配置输入 → net 构建 → 布局 → 初始 Maze → RRR → 最优解恢复 → controlbits → 独立验证
```

场景包括首轮全通、首轮失败由 RRR 修复、限时有解且当前候选非法、限时无解、不限时三次收敛、多端与同步组、默认及 verbose 日志、完整及 `-s` 稀疏输出。优先采用可重复的小型 fixture 覆盖边界，再使用 `test/config` 真实 case 验证规模与整体行为。

每个系统测试采用独立输出目录；无解测试检查没有新生成的成功 controlbits，避免把上次运行文件当作本次结果。固定可控随机因素，不用易变的精确路径作为所有用例的唯一断言。

### 6.4 带 router 的 controlbits 独立验证

现有 `check-controlbits-file` 流程重放 kiwi golden 路径再调用 Writer，适合作为 Writer 基线，但不覆盖本项目 router 实际产生的路径。两个 router 可能输出不同的合法路径，因此直接逐比特比较其各自布线结果不能证明系统错误或正确。

计划补充测试侧独立验证器，以本项目实际输出的四份 REG 文件为输入：

1. 根据输入 `register_adder.json` 和硬件寄存器定义解析地址、名称、位域与分区，检查重复、缺失、非法值和地址/名称不一致。
2. 在干净硬件状态上解码寄存器控制的 COB/TOB 连接及方向/mode，重建硬件连通图。稀疏输出先按硬件定义补齐默认值。
3. 从原始连接语义及实际布局后的端口映射独立构建预期需求，检查所有源/汇连通、不同独立 net 无意外短接、特殊电源地/多源连接符合其共享规则。
4. 检查方向、容量、mux、straight/swap 互斥、Sync lane 资源独立与等长等物理约束。
5. 将解码图中与路由相关的有效连接和最终保留路径逐一核对；区分硬件默认开关与实际承载网络的路径，不能机械要求所有寄存器默认连接都属于某个 net。
6. 核对恢复后的总线长与最终报告，证明输出使用的是保存的最优解，而非最后一个候选状态。

解码器不得调用 Writer 的编码函数或依赖 router 的 live occupancy 作结论；可复用格式读取工具和经核对的静态硬件定义。现有 `read_controlbits` 尚不支持当前四文件读回，不能假定直接调用它即可完成闭环。优先将必要解码支持限于测试范围，避免扩展生产输入格式。

验证器本身也必须被验证：用小型人工可核对映射、现有 golden 寄存器 fixture，以及有意翻转关键开关/方向/mode、断开 sink、制造短接、改错地址等负例，确认能检出真实错误。仅编码后再用同源逻辑解码的自洽检查不充分。

现有 Writer test1–test5 golden 比较继续运行。kiwi 缺失时现有脚本会 WARNING 并返回 0，测试报告必须记录为 SKIP，不能当作通过。新的 router 端到端解码验证不能依赖 kiwi 可用性。

## 9. 实施中发现的生产适配约束

- 初始 maze 以及参考 RRR 都可能连续穿过同一 COB 内的两个开关，给同一方向寄存器提出相反要求。最终解必须拒绝这种情况；搜索状态增加 Track 到达端区分，搜索与验证共同保证方向兼容。这是 controlbits 正确性修正。
- 生产输入 case2 允许 SyncNet lane 与普通分支共用一个驱动 bump。各分支保持独立的同步与路径记录；资源计数按共同驱动归并电气信号，mux 选择仍须一致。不同驱动不能共享资源；解码检查也使用这一信号关系判断短接。
- 初始 net 失败前可能占用了尚未写入 PathPackage 的局部资源，不能仅调用 `clear_path`。交接时重置资源并重占此前成功的路径；同时修正 COBUnit 重置漏掉 LU 开关的问题。
- 保留既有 golden 线长阈值。新硬件合法性检查、不同候选路径与收敛规则可能影响结果，不能为使测试通过而静默放宽阈值。

## 11. 最新验收口径（用户补充）

- case1、5、6 使用 12 列；case7、8、10、11、12 使用 13 列。先断言原 Sort + Resources + 顺序 Maze 第一轮完成所有 net，再将原路径、原排序交给 RRR。
- 不要求在短预算内得到 RRR 收敛解。无期限基准可运行几千或几万秒，不能用短时间内未收敛替代算法失败判定。
- 记录首次完整路径线长、物理合法性、RRR 各次合法解及最短线长；要求后续合法解改善线长。旧 Maze 的完成状态与硬件物理合法性分开报告；方向冲突的初始路径不计入合法解计数。
- `module_test rrr_benchmark CONFIG OUTPUT first-pass` 单独验首轮；`optimize` 接着不限时运行 RRR，并断言至少三次合法解、线长缩短、最优解合法以及提交往返路径一致。
- `rrr_system.py --test-timeout` 仅为可选测试看门狗；不指定 `--seconds` 或看门狗时不施加固定 120 秒限制。

### 后续验收澄清与停滞重试细节

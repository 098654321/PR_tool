## 加速MCf求解流程的修改


### 修改0. Gurobi的一些可以调整的参数（可以考虑应用到MCF）

- Threads

    控制 Gurobi 并行算法使用的线程数，包括并行 MIP、Barrier 和并发 LP。-1表示使用所有可用逻辑处理器，包括超过 32 个线程；0是默认值，自动选择，但会有32个线程的软上限；n表示最多使用n个线程
    通常16是一个可以尝试的值

- MIPFocus: 

    求解策略：0是默认值，自动平衡寻找可行解和证明最优；1更关注尽快找到高质量可行解；**2更关注证明当前解最优**；3更关注改善 best bound

- MIPGap

    相对最优性的gap，默认1e-4(相当于0.01%)，当相对 gap 小于该值时，Gurobi可以返回 OPTIMAL。如果只要高质量，不需要比较严格的最优，可以取1e-3。

    在求解过程中，Gurobi同时维护Incumbent（目前最好的整数可行解）&best bound（根据尚未搜索完的分支节点的 LP 松弛得到的、理论上最优解不可能突破的界），最终的最优解会夹在best bound和incumbent之间，其相对误差小于MIPGap

- MIPGapAbs 

    Incumbent & best bound之间的绝对差值小于MIPGapAbs的时候就可以认为找到最优解了。在目标函数是整数的情况下，更推荐使用这个，即“MIPGap = 1e-4, MIPGapAbs = 0.999”。注意目标函数不能有任何的浮点权重或参数，不然还是会回到浮点形式

- Symmetry

    自动对称性检测&处理。默认-1，自动处理；0禁用，1保守，2激进。Gurobi 官方指出，自动设置通常已经有效，手动改变该参数很少产生显著收益。

- Presolve

    预求解强度。-1默认自动调整；0禁用，1保守，2激进。激进 presolve 会尝试更多变量固定、约束聚合、界传播和冗余消除，可能花费更多预处理时间，但可能得到规模更小、松弛更强的模型

- PreSparsify

    控制 presolve 中的矩阵稀疏化。默认-1；0禁用；1对MIP强制启用；2对所有模型强制启用，包括 LP 和 MIP 松弛

- Heuristics：

    控制用于 MIP 可行性启发式算法的计算比例。默认0.05，近似理解为默认希望把 5% 的 MIP 时间用于启发式搜索。值越高，通常越容易发现更多、更好的可行解，但 best bound 的改善速度可能下降。

- RINS：

    -1默认，自动决策；0禁用；n表示每隔 n 个 MIP 节点运行一次 RINS。更频繁运行 RINS 会把计算从证明最优转移到寻找更好的可行解。Gurobi 官方建议优先调整 MIPFocus 等高层参数，而不是直接调整 RINS。

- Cuts：

    -1默认，自动决策；0禁用；1->2->3强度增加
    割平面的作用是强化 LP relaxation，提高 best bound（证明最优慢通常说明需要更好的 bound），从而减少分支树；代价是：
    * 根节点处理时间增加；
    * LP 行数和非零元素增加；
    * 后续每个节点的 LP 可能变慢；
    * 部分割可能几乎无效。

    割平面是求解器自动添加的一类额外线性约束，其作用是：
    * 排除 LP 松弛中的分数解；
    * 不排除任何合法整数解；
    * 使 LP 松弛更加接近原始整数可行域。

- VarBranch：

    -1默认，自动决策；0 Pseudo Reduced Cost Branching；1 Pseudo Shadow Price Branching；2 Maximum Infeasibility Branching；3 Strong Branching

    * 0:根据历史分支结果估计某变量上下分支对目标 bound 的影响。通常开销较低，适合较大的树。
    * 1:利用类似影子价格的信息评估分支变量，可能对某些 LP 结构有优势。
    * 2:优先选择 LP 值最接近整数中点的变量。例如二进制变量中，接近 0.5 的变量优先。选择成本低，但通常没有充分考虑分支后的 bound 改善。
    * 3:对候选变量实际试求上下分支 LP，再选择预计最有效的变量。单次分支决策质量高，但每个节点成本非常大。

    Gurobi 官方指出，手动修改 VarBranch 很少带来显著收益。

- 日志文件的必要设置与建议展示信息

    需要利用Gurobi原生的日志，或者自己设置相关参数记录一些信息，辅助判断参数设置对于求解过程的改善效果

    * 原生日志设置
        model.set(GRB_IntParam_OutputFlag, 1);
        model.set(GRB_StringParam_LogFile, "log_file-name");
        model.set(GRB_IntParam_LogToConsole, 0);   // 可选：只写文件
        model.set(GRB_IntParam_DisplayInterval, 5);
        model.write("settings.prm");

    * Presolve的必要展示信息

        Presolve removed ... rows and ... columns
        Presolve time: ...
        Presolved: ... rows, ... columns, ... nonzeros
        Variable types: ...

        其中presolve time说明预处理成本，rows removed说明消除约束的效果，cols removed说明消除变量的效果，nonzeros after presolve说明稀疏化效果，presolved binaries说明剩余整数搜索规模

    * MIP start信息

        User MIP start produced solution with objective ...
        Loaded user MIP start with objective ...
        User MIP start did not produce a new incumbent solution
        User MIP start violates constraint ... by ...

        需要利用这些信息确认：
        * 初始解是否完整；
        * 是否满足约束；
        * 是否成功成为 incumbent；
        * 初始目标值是多少；
        * 处理 MIP start 花费多少时间；
        * 求解过程中初始解是否很快被改进。

    * Root relaxation 信息

        Root relaxation: objective ..., ... iterations, ... seconds

        需要确认root gap信息：
        * Root gap 很大：主要是 formulation 或 bound 较弱；
        * Root gap 较小但节点很多：可能主要是对称性或分支效率问题；
        * Root 时间过长：Cuts=2、Presolve=2 等可能使根节点处理过重。

    * branch and cut过程信息

        Expl（已探索节点数量）  Unexpl（未探索节点数量）  Obj（当前节点LP松弛后的目标）  Depth（节点深度）  IntInf（当前LP解中非整数变量数量）  Incumbent（当前最好可行解）  BestBd（当前全局最好的bound）  Gap  It/Node（每个node平均LP迭代次数）  Time（累计求解时间）

        可以针对不同参数看：
        * MIPFocus=2/3：BestBd 和 gap 随时间改善速度；
        * Threads：单位时间探索的节点数、总时间和内存；
        * Symmetry：节点数量和未探索节点增长速度；
        * VarBranch：节点数量、平均深度和 It/Node；
        * Heuristics/RINS：新 incumbent 的时间、数量和来源。

    * Cut信息

        保留Gurobi日志末尾的记录：
        * 总割数量；
        * 各类型割数量；
        * 加割前后的 root bound；
        * cut generation 花费的时间；
        * cuts 加入后 LP 迭代数和节点求解速度。

### 修改2: 针对SimpleMCF模型LP松弛弱的问题进行修改

#### 修改 2.1：调整f与x关系的描述方式
当前实现里，对每个 directed flow 变量都有：
f^n_ij <= x^H_e
f^n_ji <= x^H_e
这在整数解里没问题，但 LP relaxation 很弱，因为允许：
f_ij = 0.5
f_ji = 0.5
x_e  = 0.5
也就是同一个 commodity 在同一条物理边上双向小数流动，而 x 只付 0.5 成本。建议改成：
f^n_ij + f^n_ji <= x^H_e
对每个 (commodity n, origin H, undirected edge e={i,j}) 加一条约束。如果只有一个方向存在，就退化成原来的 f <= x。
这个约束很适合你当前模型，因为它不排除任何合理整数路径，还能减少或替代现在大量 f_le_x_lower 行。

#### 修改2.2:强制net端点的o变量为1

当前 o 是 origin 对物理节点的占用变量，约束大致是：
x_e <= o_i
o_i <= sum x_e
sum_H o^H_i <= capacity_i
LP relaxation 下，终点也可以被“小数占用”。例如一个 sink 通过两条边各流 0.5，相关 x 可以是 0.5，o_sink 也可以是 0.5。真实布线里 source/sink track 一旦属于这个 origin，就应该完整占用。
建议对每个 origin group 的物理 source 和所有物理 sink 加：
o^H_source = 1
o^H_sink   = 1
或者直接把对应 o 变量下界设为 1。
这会直接强化 node capacity。这个改动不改变整数可行解，只是告诉 LP relaxation：这些端点不是可以半占用的资源。

#### 修改2.3：建模前过滤 Bus 已占用的残余容量为 0 的资源
现在 SimpleMCF 通过：
edge_capacity_override
node_capacity_override
把 Bus 已用资源变成容量约束，但从代码结构看，很多 f/x/o 变量可能已经先创建出来，再被容量约束压成 0。
建议在生成候选 arc、x、o 前就过滤：
残余 edge capacity = 0 的物理边：不创建 f / x
残余 node capacity = 0 的物理节点：不创建穿越它的非 endpoint f / o
这不是 LP tightening，而是模型缩小。需要小心 endpoint：如果 endpoint 的 residual node capacity 已经是 0，那应该直接判 infeasible 或触发 bbox/retry，而不是静默绕过。

### 修改3: 给 flow 加一个很小的二级目标，减少小数/绕圈自由度
当前目标只惩罚：
min sum x
f 不进入目标。这样在同一组 x 下，f 可以有很多等价走法，LP 和整数搜索都会有很多自由度。
可以测试一个 lexicographic 目标：
primary:   min sum x
secondary: min sum f
可以使用Gurobi multi-objective实现

### 修改4：按 origin conflict graph 分解 SimpleMCF
SimpleMCF 里不同 origin 之间只通过边容量、节点容量耦合。如果两个 origin 的候选资源集合完全不相交，它们没有必要放在同一个 Gurobi model 里。
建议构造 conflict graph：
node = origin group
edge = 两个 origin 的候选 edge 或 node 有交集
然后每个连通分量单独建模求解。这个改动不改变解空间，是 exact decomposition。

### 修改5：控制外层并行和 Gurobi 内部线程
当前 --enable-mcf-parallel 会用 std::async 同时跑 16 个 SimpleMCF，而 MCF Gurobi 没有显式设 Threads，入口在 [cob_mcf_router.cc (line 721)](/Users/jiaheng/FDU_files/Tao_group/PR_tool/PR_tool/algorithm/test_ILP/mcf/cob_mcf_router.cc:721)。Gurobi Threads=0 会自动吃机器线程。外层 16 并行叠加内层自动多线程，服务器上很可能过度并行，表现为总时间变慢、内存压力大。
建议第十版写成：
BusMCF 是单个全局模型，可以允许较多线程。
SimpleMCF 并行时，每个 unit 的 Gurobi Threads 默认设为 1。
新增一个最大并发数，例如 mcf_parallel_jobs，不要固定 16。
调度顺序按模型规模从大到小或从小到大做实验。大到小可以让长尾更早开始，小到大可以降低峰值内存。
推荐初始策略：parallel_jobs = min(物理核心数 / threads_per_model, 4 或 8)。
这个建议比盲调 Heuristics 更可能有效。

## 加速MCf求解流程的修改


0. Gurobi的一些可以调整的参数

- Threads：当前是0
- MIPFocus: 默认0；0 平衡；1 尽快找可行解；2 证明最优；3 改善界。warm start 常不可行时可试 1。
- Symmetry
- Presolve
- PreSparsify
- Heuristics：默认0.05；启发式时间占比，可行解难找时可调到 **0.3**。
- RINS：启发式频率：默认5
- Cuts：默认-1；总开关：-1 自动，0 全关，1 保守，2 激进，3 非常激进
- VarBranch：默认-1；分支变量选择：-1 自动，2 强分支，3 伪代价等


建议 1：先补计时，把慢点拆成 build / optimize / extraction
现在 solve_ms 从 stage 开始到结束，包含建模、矩阵诊断、Gurobi optimize、解提取。建议在 [cob_mcf_router.cc (line 2681)](/Users/jiaheng/FDU_files/Tao_group/PR_tool/PR_tool/algorithm/test_ILP/mcf/cob_mcf_router.cc:2681) 中对 BusMCF 和 SimpleMCF 细分：
model_build_ms
matrix_diag_ms
gurobi_optimize_ms
extract_path_ms
Gurobi Runtime、NodeCount、SolCount、ObjVal、ObjBound、MIPGap、实际 Threads
这一步很重要。否则你调 MIPFocus、Cuts、Heuristics 时不知道是在优化 Gurobi 搜索，还是 C++ 建模/诊断本身。
建议 2：控制外层并行和 Gurobi 内部线程，优先级很高
当前 --enable-mcf-parallel 会用 std::async 同时跑 16 个 SimpleMCF，而 MCF Gurobi 没有显式设 Threads，入口在 [cob_mcf_router.cc (line 721)](/Users/jiaheng/FDU_files/Tao_group/PR_tool/PR_tool/algorithm/test_ILP/mcf/cob_mcf_router.cc:721)。Gurobi Threads=0 会自动吃机器线程。外层 16 并行叠加内层自动多线程，服务器上很可能过度并行，表现为总时间变慢、内存压力大。
建议第十版写成：
BusMCF 是单个全局模型，可以允许较多线程。
SimpleMCF 并行时，每个 unit 的 Gurobi Threads 默认设为 1。
新增一个最大并发数，例如 mcf_parallel_jobs，不要固定 16。
调度顺序按模型规模从大到小或从小到大做实验。大到小可以让长尾更早开始，小到大可以降低峰值内存。
推荐初始策略：parallel_jobs = min(物理核心数 / threads_per_model, 4 或 8)。
这个建议比盲调 Heuristics 更可能有效。
建议 3：把 --enable-mcf-obj 改成两阶段策略
当前命令打开了 --enable-mcf-obj，SimpleMCF 目标是 min Σ x。日志显示 warm start 对所有 SimpleMCF commodity 都成功了，但 Gurobi 仍要证明 min_sum_x 最优。这类“已有可行解但证明最优慢”的情况，MIPFocus=1 未必最合适。
建议第十版分三种模式：
fast_feasible：只要求可行，SimpleMCF 不设 min Σx，或者 warm start 全部成功且资源检查通过时直接接受。
quality_fast：保留 min Σx，但允许 MIPGap=1%~5% 或 SolutionLimit=1 后接受 incumbent。
exact_opt：当前行为，证明最优，适合小 case 或最终质量评估。
如果使用 TimeLimit、SolutionLimit、NodeLimit 这类提前停止，必须同步修改 solution class：只要 SolCount > 0，就应提取 incumbent，标成 Suboptimal 或新增 Feasible，不能像现在那样把 TIME_LIMIT 一律当失败。
建议 4：Gurobi 参数建议要按目标分类
第十版已有 Gurobi 参数列表，但建议不要直接暴露一堆 knob。更好的写法是“预设 + 少数参数”。
对于当前 case7 这种 warm start 已有可行解、慢在证明最优的情况，优先试：
Threads=1，用于 SimpleMCF 并行模式。
MIPGap=0.01 或 0.05，接受近似最优。
MIPFocus=2，偏向证明界限；如果发现经常找不到可行解，再试 MIPFocus=1。
Presolve=2、PreSparsify=1。
Symmetry=2，因为 SimpleMCF 本身对称性强。
Heuristics=0.1~0.3 只在 incumbent 难找时有意义；当前 warm start 成功，收益可能有限。
Cuts 先用自动或保守，不建议一开始强行 3。
建议 5：把 pre-route 完整成功时作为可行解快速返回
当前 SimpleMCF warm start 已经在每个 unit 内做 BFS，并用 used_edges / used_nodes 避免冲突，相关逻辑在 [cob_mcf_router.cc (line 1853)](/Users/jiaheng/FDU_files/Tao_group/PR_tool/PR_tool/algorithm/test_ILP/mcf/cob_mcf_router.cc:1853)。case7 日志里所有 SimpleMCF warm start 都是 failed_commodities=0。
可以新增一个严格校验：
所有 commodity 都有 path。
每条物理边容量不超过 Bus residual。
每个物理节点容量不超过 Bus residual。
每个 child 的 path 连续且 src/snk 正确。
多扇出 origin 内共享资源允许，origin 间不冲突。
如果校验通过，在 fast_feasible 模式下直接接受，不再建 SimpleMCF Gurobi 模型。这个对当前 case7 可能是数量级加速。
建议 6：减少 SimpleMCF 模型行数
当前 SimpleMCF 最大行数主要来自：
f_le_x_lower
flow_conservation
x_le_o
o_le_sum_x
可以考虑两个等价或近似等价的压缩：
把每条有向边的 f_ij <= x_e、f_ji <= x_e 合并为：
f_ij + f_ji <= x_e
对单个 child 来说，这通常更强，也能减少约一半 lower link 行。

把每条 incident edge 的 x_e <= o_i 改为每个 origin-node 一条 big-M：
Σ_{e∈δ(i)} x_e <= deg(i) * o_i
再保留 o_i <= Σ x_e。
这样 x_le_o 可从“每条边两行”降到“每个 origin-node 一行”。

这两项属于模型层修改，应该用小 case 验证解的等价性和 wire length 是否变化。
建议 7：预剪枝 Bus 已占资源和零容量资源
SimpleMCF 现在用 edge_capacity_override / node_capacity_override 把 Bus 已用资源变成容量约束，但很多变量仍可能先创建出来，再被约束压成 0。建议在生成 f/x 候选前就过滤：
residual edge capacity 为 0 的物理边，不创建 SimpleMCF f/x。
residual node capacity 为 0 的节点，非当前端点相关边不创建。
对应的 edge_capacity 行也只为实际候选 x 边创建，不必固定每个 unit 都建 5616 行。
这和第六版“范围外不建变量”的思想一致，只是把 Bus residual 也纳入可行图裁剪。
建议 8：把 RectHull 改成更精细的 allowed-region
第九版 PNnet/TTB 多扇出 origin 使用 child bbox 的 RectHull。这保证共享主干，但矩形会包含大量无关空白区域。unit8-15 的大模型很可能和这些 hull 过大有关。
第十版可以提出一个更强版本：
对每个 origin group，不再只存矩形 bbox。
存一个 allowed arc/node mask。
mask 来源是 child path bbox 的并集，加 warm-start tree 的路径区域，再做一圈可选 expand。
bbox expand 时扩 mask 的边界，而不是扩整个 RectHull。
这是比较大的工程改动，但从算法建模上最干净：它减少变量，同时保留共享树形路径的空间。
建议 9：按 origin 冲突图分解 SimpleMCF
SimpleMCF unit 内不同 origin group 之间只通过边/节点容量耦合。如果两个 origin 的候选资源集合完全不相交，它们没必要放进同一个 Gurobi 模型。
可以建一个冲突图：
点：origin group。
边：两个 origin 的候选 edge/node 集合有交集，或都接触同一 Bus residual 紧张区域。
每个连通分量单独建 SimpleMCF 子模型。
这对 unit13/14/15 这种 origin group 多的情况尤其有价值。它比直接 16 unit 并行更细，也能降低单个模型的分支复杂度。
建议 10：--show-pre-route 不建议用于性能测试
--show-pre-route 会自动开启 pre-routing，而且求解后还会为了打印 pre-route usage 再汇总 warm start 和资源使用。当前日志还没跑到这一步，但完整运行会增加额外日志和统计成本。性能测试建议先去掉它，只保留必要 timing；调通后再打开做可视化分析。
我建议第十版文档的优先顺序
计时拆分和 Gurobi 状态扩展，先获得可靠观测。
SimpleMCF 并行数 + Gurobi Threads 控制。
fast feasible / quality fast / exact opt 三种求解模式。
pre-route 完整成功直接接受。
SimpleMCF 约束压缩和 residual 预剪枝。
allowed-region mask 和 origin 冲突图分解，作为较大版本优化。
